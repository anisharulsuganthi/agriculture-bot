## 1. Conventions

### 1.1 Base URL and absolute URLs

All paths in this document are relative to the base URL. Always build absolute
URLs from `API_BASE_URL` rather than hard-coding a host. The dev default is
`http://localhost:8000`; the app binds to loopback `127.0.0.1:8000`.

### 1.2 Error shape

Every error response is a single JSON object with a `detail` key:

```json
{ "detail": "Authentication required. Send 'Authorization: Bearer <token>' from /api/auth/login." }
```

`detail` is a **string** for errors raised by the application. It is an **array of
validation objects** for `422` responses produced by Pydantic:

```json
{
  "detail": [
    {
      "type": "string_too_short",
      "loc": ["body", "password"],
      "msg": "String should have at least 4 characters",
      "input": "ab"
    }
  ]
}
```

The validation object fields are `loc` (array of `string`/`int`, the failing
location), `msg` (string), `type` (string) and optionally `input` and `ctx`.

Unhandled server errors are caught by a global exception handler and returned as
a generic `500` so that stack traces and secrets never reach the client:

```json
{ "detail": "Internal server error. Check the server logs." }
```

The full exception, with registered secrets redacted, is written to the server log
only.

### 1.3 Response headers

| Header | When present | Meaning |
|---|---|---|
| `X-Process-Time-Ms` | Every response | Wall-clock server processing time in milliseconds, one decimal place. Added by `timing_middleware` (e.g. `x-process-time-ms: 2.0`). |
| `WWW-Authenticate: Bearer` | `401` from the auth dependency | Signals the expected credential scheme. |
| `Retry-After` | `429` from the rate limiter | Seconds to wait, equal to the rate-limit window. |

CORS is enabled for the origins in `CORS_ORIGINS` (default
`http://localhost:5500`, `http://127.0.0.1:5500`, `http://localhost:8000`,
`http://127.0.0.1:8000`).

### 1.4 Timestamps

All timestamps are ISO-8601 strings, but they are **naive** - no `Z` suffix and no
UTC offset is emitted. Consumers must not infer a zone from the string.

Two different clocks are used in the code, which matters when comparing records:

| Field group | Source | Effective zone |
|---|---|---|
| `disease_predictions.created_at`, `farming_sessions.ended_at`, `animal_sessions.created_at`, `animal_sessions.ended_at`, `animal_daily_logs.date` | `datetime.utcnow()` | UTC |
| `farming_sessions.created_at`, `daily_logs.date`, weather `timestamp` | `datetime.now()` | Server local time |

Date-only values (`generated_on`, forecast `date`, `resource_timeline.dates`) use
`YYYY-MM-DD`.

### 1.5 Numbers and currency

All monetary values are plain JSON numbers (never formatted strings) in the API
responses, rounded to 2 decimals by the route that produces them. They are
currency-agnostic: the code stores no currency code. The Indian Rupee sign appears
only inside free-text display strings generated by the market simulation
(`forecast`, `current_price`, `forecast_price` inside
`/api/market/intelligence`), and in the advisory email body. Treat prices as
currency values in the units the producer states (`unit` field), not as
pre-formatted display strings.

### 1.6 Enumerations

| Enumeration | Values | Where |
|---|---|---|
| Prediction `status` | `healthy`, `diseased`, `uncertain`, `unknown` | `/api/predict/disease` |
| Prediction `severity` | `None` (healthy), `High`, `Moderate` | `/api/predict/disease` |
| Weather `data_source` | `openweathermap`, `simulated` | weather blocks |
| Market `data_source` | `simulated` | `/api/market/intelligence` |
| Risk `risk_level` | `Low`, `Medium`, `High`, `Unknown` | `disease_risk`, `disease_risk_forecast` |
| Watering `rule_fired` | `default`, `rain_expected`, `low_moisture`, `heat_stress`, `high_humidity`, `sandy_soil`, `clay_soil` | `watering` |
| Fertilizing `rule_fired` | `default`, `rain_expected`, `heat_stress`, `ideal_moisture`, `routine` | `fertilizing` |
| Advisory `method` | `rule_based_decision_engine` | `watering`, `fertilizing`, `disease_risk`, `disease_risk_forecast`, `inputs_summary` |
| ET0 `method` | `simplified_hargreaves_type_estimate` | `et0_estimate` |

### 1.7 Empty-collection behaviour

Endpoints that return aggregates over user data never fail on an empty database.
They return zeroed values:

- `avg_confidence` is `0.0` (not `null`) when there are no predictions.
- `profit_margin_percent` is `0.0` when `total_investment` is `0`.
- `cost_breakdown.data`, `session_performance`, the `*_distribution` objects and
  `resource_timeline` are empty.
- `disease_risk_forecast` is `{"risk_level": "Unknown", "highest_risk_day": null, "days": [], "method": ...}` for an empty forecast.
- `/api/market/intelligence` returns empty `market_data`, `news_feed` and
  `recommendations` arrays with `commodities_tracked: 0` when the user has no
  sessions.
- List endpoints return `[]` with status `200`, never `404`.

### 1.8 Bounded query parameters

Two query parameters are clamped server-side rather than rejected:

| Parameter | Declared default | Effective range | Clamp code |
|---|---|---|---|
| `GET /api/predictions` `limit` | `20` | 1 - 200 | `max(1, min(int(limit or 20), 200))` |
| `GET /api/sessions/{id}/weather` `days` | `5` | 1 - 5 | `max(1, min(days, 5))` |

A non-integer value for either still produces `422` because Pydantic validates
the type first.

## 2. Authentication

### 2.1 Token flow

```
POST /api/auth/register   ->  { access_token, token_type, expires_in_minutes, user }
POST /api/auth/login      ->  { access_token, token_type, expires_in_minutes, user }

every data request        ->  Authorization: Bearer <access_token>
```

1. `POST /api/auth/register` or `POST /api/auth/login` returns an `access_token`.
2. The client stores it and sends it as `Authorization: Bearer <access_token>` on
   every route that requires authentication.
3. The token is a JWT signed with `JWT_SECRET` using the algorithm in
   `JWT_ALGORITHM` (default `HS256`). Claims: `sub` (the user id as a string),
   `email`, `name`, `iat`, `exp`, and `iss` = `smartfarm-adis`. The server
   **requires** both `exp` and `sub` and verifies the issuer on decode.
4. Token lifetime is `ACCESS_TOKEN_EXPIRE_MINUTES`, default `720` minutes, and is
   returned to the client as `expires_in_minutes` on both register and login so
   the client can schedule a refresh without guessing.
5. `get_current_user` decodes the token, reads `sub`, and loads that user from
   the database on every request. A token that decodes but points at a deleted
   account is rejected with `401`.

There is no refresh token and no logout endpoint: a token is valid until it
expires, and "logging out" is a client-side discard. Rotating `JWT_SECRET`
invalidates every outstanding token and every outstanding password-reset OTP.

### 2.2 Passwords

- Stored with bcrypt and a per-user random salt.
- Version-1 records stored `sha256(password + static_salt)` as a bare 64-character
  hex digest. Those hashes are still **verifiable**, and the stored value is
  transparently re-hashed with bcrypt on the next successful login.
- `validate_password_strength` rejects a password that is shorter than
  `PASSWORD_MIN_LENGTH` (default `8`), that is only whitespace, that exceeds 72
  UTF-8 bytes (bcrypt silently truncates beyond 72 bytes, which would make two
  different passwords interchangeable), or - in a production environment only -
  that is digits only.
- Because the Pydantic model only enforces `min_length=4` while the route enforces
  the strength policy, a 4-7 character password passes schema validation and is
  then rejected by the route with `400`.

### 2.3 Password reset

```
POST /api/auth/forgot-password  { email }
   -> always 200 with the same generic message, whether or not the account exists
   -> for a real account: a 6-digit OTP is emailed, valid for 10 minutes, max 5 attempts

POST /api/auth/reset-password  { email, otp, new_password }
   -> 200 on success, 400 on unknown/expired/incorrect code, 429 after 5 attempts
```

The OTP is never stored in plaintext. Only a keyed digest (HMAC-SHA256 keyed with
`JWT_SECRET`) is persisted, so a leaked database row cannot be replayed against
`/api/auth/reset-password`. `/api/auth/forgot-password` returns the identical
generic response for registered and unregistered addresses, so the endpoint
cannot be used to enumerate accounts. A delivery failure is logged and
deliberately **not** surfaced, because returning an error only for real accounts
would re-enable enumeration in a misconfigured deployment.

### 2.4 Removal of the `X-User-Id` header

Version 1 authenticated every request with a client-supplied `X-User-Id` header.
That is a spoofable identity claim, not authentication, so it is **off by
default**:

- `ALLOW_LEGACY_USER_HEADER` defaults to `false`. With the default setting, an
  `X-User-Id` header is ignored for authentication and the request is rejected
  with `401` and
  `{"detail": "Authentication required. Send 'Authorization: Bearer <token>' from /api/auth/login."}`.
  Verified against the running service: `GET /api/sessions` with `X-User-Id: 1`
  and no `Authorization` header returns `401` with `WWW-Authenticate: Bearer`.
- The header parameter still appears in the generated OpenAPI schema for every
  authenticated route. That is an artefact of the dependency signature
  (`app/deps.py` declares the parameter so it can be read when legacy auth is
  explicitly enabled), **not** an indication that the header works. Always
  authenticate with `Authorization: Bearer <token>`.
- If an operator sets `ALLOW_LEGACY_USER_HEADER=true`, the header is accepted
  again, a non-numeric value produces `401 {"detail": "Invalid X-User-Id header."}`,
  and every use is logged at warning level so the migration can be verified.
  `validate_startup()` reports a configuration problem if the flag is on in a
  production environment.
- When both headers are present the `Authorization` token always wins; the legacy
  header is only consulted when no usable Bearer token is supplied.

### 2.5 Ownership rules

Every user-owned resource is loaded through a helper in `backend/app/deps.py`
rather than queried directly, which is what closes the Version-1 IDOR bugs:

| Helper | Applies to | Missing row | Wrong owner / NULL owner |
|---|---|---|---|
| `get_owned_plant_session` | `FarmingSession` | `404 {"detail": "Farming session not found."}` | `403` |
| `get_owned_animal_session` | `AnimalSession` | `404 {"detail": "Animal session not found."}` | `403` |

The two `403` messages are distinct:

- another account's row: `{"detail": "You do not have access to farming session 7."}` (or `animal session`)
- a legacy row with `user_id IS NULL`: `{"detail": "farming session 7 has no owner (legacy data). Run the data migration first."}`

Two read endpoints are filtered by owner inside the query instead of going
through a helper, so they **do not** return `403` or `404` for someone else's id -
they simply produce empty aggregates. These are
`GET /api/dashboard/analytics?session_id=` and
`GET /api/animals/dashboard/analytics?session_id=`.

### 2.6 Which routes need a token

| Route | Auth required |
|---|---|
| `GET /api/health` | No |
| `GET /api/system/info` | No |
| `GET /api/crops` | No |
| `POST /api/auth/register` | No |
| `POST /api/auth/login` | No |
| `POST /api/auth/forgot-password` | No |
| `POST /api/auth/reset-password` | No |
| All other 24 routes | Yes - `Authorization: Bearer <token>` |

## 5. Authentication endpoints

### 5.1 `POST /api/auth/register`

Create an account and receive a token immediately - no separate login is needed
after registration.

**Request body** - `UserRegister`, `application/json`

| Field | Type | Required | Validation |
|---|---|---|---|
| `name` | string | Yes | 2 - 100 characters. Trimmed before storage. |
| `email` | string | Yes | 5 - 100 characters. Trimmed and lowercased, then must contain `@` and a `.` in the domain part. |
| `password` | string | Yes | 4 - 200 characters at the schema level, then the strength policy applies: minimum `PASSWORD_MIN_LENGTH` (default 8), not blank, at most 72 UTF-8 bytes, and not digits-only in production. |

**Response `200`**

| Field | Type | Meaning |
|---|---|---|
| `status` | string | `"success"`. |
| `message` | string | `"Account created successfully!"`. |
| `user.id` | integer | New account id. |
| `user.name` | string | Stored, trimmed name. |
| `user.email` | string | Stored, normalised email. |
| `user.created_at` | string or null | Account creation time, ISO-8601 naive UTC, or `null`. |
| `access_token` | string | JWT to send as `Authorization: Bearer <access_token>`. |
| `token_type` | string | Always `"bearer"`. |
| `expires_in_minutes` | integer | Token lifetime in minutes, from `ACCESS_TOKEN_EXPIRE_MINUTES` (default `720`). |

**Errors**

| Status | Trigger | `detail` |
|---|---|---|
| `400` | Password fails the strength policy | The policy message, e.g. `"Password must be at least 8 characters long."` |
| `400` | Email already registered | `"An account with this email already exists."` |
| `422` | Schema violation (missing field, length, malformed email) | Array of validation objects |
| `429` | More than `REGISTER_RATE_LIMIT` (default `20`) requests from one IP within `RATE_LIMIT_WINDOW_SECONDS` (default `300`s) | `"Too many requests for register. Please wait and try again."` + `Retry-After` |
| `500` | Unhandled server error | Generic message |

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name": "Demo Farmer", "email": "demo.farmer@example.com", "password": "Agri#2026x"}'
```

**Example response**

```json
{
  "status": "success",
  "message": "Account created successfully!",
  "user": {
    "id": 1,
    "name": "Demo Farmer",
    "email": "demo.farmer@example.com",
    "created_at": "2026-09-25T09:14:02.113645"
  },
  "access_token": "<access_token>",
  "token_type": "bearer",
  "expires_in_minutes": 720
}
```

### 5.2 `POST /api/auth/login`

Exchange credentials for a token.

**Request body** - `UserLogin`, `application/json`

| Field | Type | Required | Validation |
|---|---|---|---|
| `email` | string | Yes | 3 - 100 characters. Trimmed and lowercased. No format check here, so a malformed address simply fails the lookup. |
| `password` | string | Yes | 1 - 200 characters. No strength policy on login. |

**Response `200`** - identical shape to register (`status`, `message`, `user`,
`access_token`, `token_type`, `expires_in_minutes`), with
`message = "Logged in successfully!"`.

**Errors**

| Status | Trigger | `detail` |
|---|---|---|
| `400` | Unknown email **or** wrong password - the two are not distinguished | `"Invalid email or password."` |
| `422` | Schema violation | Array of validation objects |
| `429` | More than `LOGIN_RATE_LIMIT` (default `10`) attempts from one IP within the window | `"Too many requests for login. Please wait and try again."` + `Retry-After` |
| `500` | Unhandled server error | Generic message |

Every failed attempt is logged at warning level with the submitted address. A
successful login against a legacy hash transparently rewrites the stored hash to
bcrypt.

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "demo.farmer@example.com", "password": "Agri#2026x"}'
```

**Example response**

```json
{
  "status": "success",
  "message": "Logged in successfully!",
  "user": {
    "id": 1,
    "name": "Demo Farmer",
    "email": "demo.farmer@example.com",
    "created_at": "2026-09-25T09:14:02.113645"
  },
  "access_token": "<access_token>",
  "token_type": "bearer",
  "expires_in_minutes": 720
}
```

### 5.4 `POST /api/auth/forgot-password`

Request a password-reset OTP. **Always answers `200` with the same generic
message**, whether or not the address is registered, so the endpoint cannot be
used to enumerate accounts.

**Request body** - `ForgotPasswordRequest`, `application/json`

| Field | Type | Required | Validation |
|---|---|---|---|
| `email` | string | Yes | 3 - 100 characters. Trimmed and lowercased. |

**Response `200`**

| Field | Type | Meaning |
|---|---|---|
| `status` | string | `"success"`. |
| `message` | string | Always `"If that email is registered, a reset code has been sent."` |

For a real account, a numeric OTP of `OTP_LENGTH` digits (default `6`) is
generated, its keyed digest is stored with an expiry of `OTP_EXPIRY_MINUTES`
(default `10`) minutes and an attempt counter reset to `0`, and the code is
emailed. For an unknown address nothing is written and nothing is sent; the server
logs the fact at info level. A delivery failure is logged as an error and
deliberately not surfaced.

**Errors**

| Status | Trigger | `detail` |
|---|---|---|
| `422` | Schema violation | Array of validation objects |
| `429` | More than `FORGOT_RATE_LIMIT` (default `5`) requests from one IP within the window | `"Too many requests for forgot. Please wait and try again."` + `Retry-After` |
| `500` | Unhandled server error | Generic message |

There is deliberately no `400` for "unknown email" - see the note above.

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/auth/forgot-password \
  -H "Content-Type: application/json" \
  -d '{"email": "demo.farmer@example.com"}'
```

**Example response**

```json
{
  "status": "success",
  "message": "If that email is registered, a reset code has been sent."
}
```

### 5.5 `POST /api/auth/reset-password`

Complete a password reset using the emailed OTP.

**Request body** - `ResetPasswordRequest`, `application/json`

| Field | Type | Required | Validation |
|---|---|---|---|
| `email` | string | Yes | 3 - 100 characters. Trimmed and lowercased. |
| `otp` | string | Yes | 4 - 10 characters. Issued codes are `OTP_LENGTH` digits (default `6`). |
| `new_password` | string | Yes | 4 - 200 characters at the schema level, then the same strength policy as registration (default minimum 8, not blank, at most 72 bytes, not digits-only in production). |

**Response `200`**

| Field | Type | Meaning |
|---|---|---|
| `status` | string | `"success"`. |
| `message` | string | `"Password updated successfully! You can now log in."` |

On success the stored hash is replaced, the OTP digest and expiry are cleared and
the attempt counter is reset. Existing tokens are **not** revoked - the client
must log in again to obtain a new one.

**Errors**

| Status | Trigger | `detail` |
|---|---|---|
| `400` | Unknown email, or no OTP outstanding | `"Invalid or expired reset code."` |
| `400` | OTP past its expiry | `"Reset code has expired. Request a new one."` |
| `400` | OTP digest mismatch (increments and persists the attempt counter) | `"Incorrect reset code."` |
| `400` | New password fails the strength policy | The policy message |
| `422` | Schema violation | Array of validation objects |
| `429` | Attempt counter has reached `OTP_MAX_ATTEMPTS` (default `5`) | `"Too many incorrect attempts. Request a new reset code."` |
| `429` | More than `RESET_RATE_LIMIT` (default `10`) requests from one IP within the window | `"Too many requests for reset. Please wait and try again."` + `Retry-After` |
| `500` | Unhandled server error | Generic message |

Note that the `429` for exhausted OTP attempts has no `Retry-After` header; only
the rate-limiter `429` carries one.

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/api/auth/reset-password \
  -H "Content-Type: application/json" \
  -d '{"email": "demo.farmer@example.com", "otp": "482913", "new_password": "Agri#2026x"}'
```

**Example response**

```json
{
  "status": "success",
  "message": "Password updated successfully! You can now log in."
}
```

## 6. Disease detection

### 6.1 `POST /api/predict/disease`

Classify a leaf image. Returns the top-k class probabilities, a low-confidence
flag, an annotated preview and three advisory steps.

Requires `Authorization: Bearer <token>`.

**Request** - `multipart/form-data`

| Part | Type | Required | Default | Notes |
|---|---|---|---|---|
| `image` | file | Yes | - | The leaf photograph. |
| `crop_type` | string | No | `"Unknown"` | Run through `normalize_crop_type`, so `potato`, `Potato` and `aloo` all become `Potato`. An unrecognised value is title-cased rather than remapped, so a genuinely new crop stays visible. |
| `symptoms` | string | No | `""` | Free-text farmer description. Truncated to 2000 characters before storage. |
| `location` | string | No | `"Tamil Nadu, India"` | Used in the advisory text ("confirm locally approved treatments for ..."). |

**Upload validation** (checked before inference, in this order)

| Check | Failure status | `detail` |
|---|---|---|
| Part present with a filename | `400` | `"No image file was provided."` |
| `content_type` in `ALLOWED_IMAGE_TYPES` (default `image/jpeg`, `image/png`, `image/webp`) | `400` | `"Unsupported file type '<type>'. Allowed: image/jpeg, image/png, image/webp."` |
| Filename ends with an allowed extension (default `.jpg`, `.jpeg`, `.png`, `.webp`) | `400` | `"Unsupported file extension. Allowed: .jpg, .jpeg, .png, .webp."` |
| Size not over `MAX_UPLOAD_BYTES` (default 8 MB) | `413` | `"Image is too large. Maximum upload size is 8 MB."` |
| Size greater than zero | `400` | `"The uploaded file is empty."` |
| Decodable by Pillow | `400` | `"Unreadable image file: <reason>"` |
| Width and height at least `MIN_IMAGE_DIMENSION` (default 32 px) | `400` | `"Image is too small (640x480px). Minimum dimension is 32px."` |
| Width x height not over `MAX_IMAGE_PIXELS` (default 25,000,000) | `400` | `"Image resolution is too large to process safely."` (decompression-bomb guard) |

Inference runs in the worker thread pool, so the event loop keeps serving other
requests during a prediction.

**Response `200`**

| Field | Type | Meaning |
|---|---|---|
| `prediction.id` | integer | Stored detection record id. |
| `prediction.disease_name` | string | Top-1 class label exactly as the model returns it (class names may contain `_` or `___`). |
| `prediction.confidence_score` | number | Top-1 probability as a percentage, 0 - 100. |
| `prediction.is_healthy` | boolean | `true` when the top-1 label contains the substring `healthy`. Derived from the label, not hardcoded. |
| `prediction.severity` | string | `None` when healthy, otherwise `High` or `Moderate` from a keyword lookup over the class name. Heuristic, not clinically validated. |
| `prediction.status` | string | `healthy`, `diseased`, `uncertain` or `unknown`. See below. |
| `prediction.confident` | boolean | `true` when `confidence_score >= confidence_floor`. |
| `prediction.requires_expert_review` | boolean | Exact inverse of `confident`. |
| `prediction.confidence_floor` | number | The floor in force, echoed so the client can display it. |
| `prediction.detections` | object[] | Top-k results, highest score first. Each item: `label` (string), `score` (number, percentage), `box` (always `null`). |
| `prediction.annotated_image_base64` | string | Base64 JPEG of the upload with the top-1 label and score drawn as a caption bar. **No `data:` URL prefix.** |
| `prediction.annotation_type` | string | Always `"prediction_caption"`. The model classifies; it does not localise, so this is a caption and not a bounding box or a heat map. |
| `prediction.inference_ms` | number | Model forward-pass time in ms. |
| `prediction.device` | string | `cpu` or `cuda`. |
| `prediction.created_at` | string or null | Record timestamp, ISO-8601 naive UTC. |
| `prediction.crop_type` | string | The canonical crop name actually stored. |
| `cure` | object[] | Three advisory steps. Each item: `step` (integer), `action` (string), `details` (string), `source` (string). |
| `cure_source` | string | `source` of the first step, or `"unknown"` if the list is empty. |
| `notice` | string or null | Set only when `confident` is `false`. |

**Meaning of `prediction.status`**

- `healthy` - top-1 score is at or above the confidence floor and the label is a healthy class.
- `diseased` - top-1 score is at or above the floor and the label is not healthy.
- `uncertain` - the top score is **below** the confidence floor (`ML_CONFIDENCE_FLOOR`, default `40.0`). The label is still returned so the history is complete, but the result is explicitly not a disease verdict: `confident` is `false`, `requires_expert_review` is `true`, and `notice` asks for a clearer daylight close-up or an expert.
- `unknown` - the pipeline returned no detections at all.

**Errors**

| Status | Trigger | `detail` |
|---|---|---|
| `400` | Upload validation or image decode/dimension failures | See the upload validation table |
| `401` | Missing, invalid or expired token | See [5.3](#53-get-apiauthme) |
| `413` | File larger than `MAX_UPLOAD_BYTES` | `"Image is too large. Maximum upload size is 8 MB."` |
| `422` | `image` part absent, or a form field has the wrong type | Array of validation objects |
| `500` | Model missing, load failure, or any inference/runtime error | `"Disease prediction failed. Please retry."` (the real cause is in the server log) |

```bash
curl -X POST http://127.0.0.1:8000/api/predict/disease \
```

## 9. Advisory

### 9.1 `GET /api/sessions/{session_id}/recommendations`

The full advisory for a plant session: watering, fertilising, current disease
risk, multi-day disease risk, a reference evapotranspiration estimate, and a
transparent summary of the inputs used.

Calling this route writes two rows to the recommendation log (one for watering,
one for fertilising) with the current timestamp. Repeated calls therefore append
history rather than overwrite it.

Requires `Authorization: Bearer <token>`. Ownership is enforced.

**Path parameters**

| Name | Type | Required |
|---|---|---|
| `session_id` | integer | Yes |

**Request:** no query or body parameters.

**Soil moisture is an estimate, not a measurement.** No in-situ soil sensor is
deployed. `estimate_soil_moisture` derives a percentage from soil type, whether
the session was watered today, days since the last logged watering, the
next-24-hour rain probability and the current temperature, then applies a soil
retention factor (`sandy` 0.6, `red` 0.85, `loam` 1.0, `alluvial` 1.1, `black`
1.3, `clay` 1.35, anything else 1.0) and clamps to 5 - 95. The function is
deterministic, so two identical requests return the same number. See
[Data provenance](#12-data-provenance).

**Response `200`**

| Field | Type | Meaning |
|---|---|---|

**Rule thresholds** (documented assumptions, not validated against field data)

Watering rules, evaluated in this order:

| Order | `rule_fired` | Condition |
|---|---|---|
| 1 | `rain_expected` | 24-hour rain probability `> 50%` |
| 2 | `low_moisture` | estimated soil moisture `< 30%` |
| 3 | `heat_stress` | temperature `> 35 C` and rain probability `< 20%` |
| 4 | `high_humidity` | humidity `> 80%` |
| 5 | `sandy_soil` | soil type is `sandy` |
| 6 | `clay_soil` | soil type is `clay` |
| 7 | `default` | otherwise |

Fertilising rules, evaluated in this order:

| Order | `rule_fired` | Condition |
|---|---|---|
| 1 | `rain_expected` | 24-hour rain probability `> 40%` |
| 2 | `heat_stress` | temperature `> 38 C` |
| 3 | `ideal_moisture` | estimated soil moisture between 40% and 60% inclusive |
| 4 | `routine` | otherwise |

Disease risk bands: `High` when humidity `> 80%` and temperature between 25 and
32 C; `Medium` when humidity `> 60%` and temperature between 20 and 35 C; `Low`
otherwise.

### 9.2 `POST /api/sessions/{session_id}/notify`

Email the current advisory for a session to the authenticated account's own
address.

The request body's `email` field is accepted but **advisory only**: the recipient
is always the token user's own address. Version 1 accepted any recipient, which
made this an open relay. That field is never used as a delivery target.

This route computes the advisory with exactly the same inputs as
`/api/sessions/{session_id}/recommendations`, including the same soil-moisture
estimate and the same real `watered_today` flag, so the email and the dashboard
cannot disagree.

Requires `Authorization: Bearer <token>`. Ownership is enforced.

**Path parameters**

| Name | Type | Required |
|---|---|---|
| `session_id` | integer | Yes |

**Request body** - `NotifyRequest`, `application/json`

| Field | Type | Required | Validation | Meaning |
|---|---|---|---|---|
| `email` | string or null | No | max 100 chars, default `null` | Ignored for delivery. Kept only so the existing client keeps working. |

The body is required by the OpenAPI schema (`requestBody.required: true`), so
send at least `{}` if you have no reason to pass an address.

**Response `200`**

| Field | Type | Meaning |
|---|---|---|
| `status` | string | `"success"`. |
| `message` | string | `"Advisory sent to your account email address."` |
| `recipient` | string | The address actually used, i.e. the account's own address. |
| `advice` | object | The advisory that was sent: `watering`, `fertilizing` and `disease_risk`, each with the same field set as in [9.1](#91-get-apisessionssession_idrecommendations). |

**Errors**

| Status | Trigger | `detail` |
|---|---|---|

| `503` | Live weather unavailable **and** `ALLOW_SIMULATED_WEATHER=false` | Weather-unavailable message |
| `500` | Unhandled server error | Generic message |

### 10.1 `GET /api/dashboard/summary`

Requires `Authorization: Bearer <token>`.

**Request:** no path, query or body parameters.

**Response `200`**

|---|---|---|
| `total_investment` | number | Sum over all sessions of `seed_qty * cost_per_seed + total_land_cost + fertilizer_qty * cost_per_fertilizer`, **plus** for every daily log with `fertilized = true`, `fertilizer_amount * cost_per_fertilizer`. Rounded to 2 decimals. |

| `422` | Schema violation |
| `500` | Unhandled server error |

### 10.2 `GET /api/dashboard/analytics`

## 12. Data provenance

This section states, in one place, which numbers in this API are measured,
which are estimated, and which are simulated. Nothing else in this document
should be read as making a stronger claim than the one made here.

### 12.1 `/api/market/intelligence` is simulated demonstration data

Every price, trend, forecast price, mandi distance, news headline and selling
recommendation returned by `/api/market/intelligence` is **generated locally**.
No live mandi (market) price feed is integrated with the system.

The generation logic is isolated in `backend/simulation_service.py`. It is
deterministic per commodity and per calendar day (a SHA-256 of
`commodity|type|date`), so a value does not change between two requests minutes
apart, and every commodity changes together the next day. The purpose is UI/UX
demonstration, not market reporting.

Provenance is machine-readable in the response itself, so a client never has to
guess:

| Signal | Where it appears |
|---|---|
| `data_source: "simulated"` | Top level and on every `market_data`, `news_feed` and `recommendations` record |
| `disclaimer` | Top level and on every `market_data` and `recommendations` record |
| `"DEMONSTRATION"` in the text | Every `headline` and every recommendation `title` |
| `"no live feed integrated"` in the text | `news_feed[].source` and `recommendations[].best_location` |
| `generated_on` | The date component of the determinism seed |

The `mandis` list is also fixed demonstration geography (Coimbatore, Salem,
Chennai) with generated distances. Treat none of it as a market quotation.

### 12.2 Soil moisture in `/api/sessions/{session_id}/recommendations` is an estimate

**No soil moisture sensor is deployed.** The `soil_moisture` value in the
recommendations response (and the identical value used inside `watering` and
`fertilizing`) is a deterministic **estimate** computed by
`estimate_soil_moisture` in `backend/recommendation_engine.py` from:

1. a base of 65%,
2. `+20` if the session was logged as watered today,
3. `-6` per day since the last logged watering, beyond the first day,
4. `-12` if the current temperature is at least 35 C, or `+5` if at most 20 C,
5. `+ rain_probability_24h * 0.25` (clamped to 0-100 first),
6. multiplied by a soil retention factor (`sandy` 0.6, `red` 0.85, `loam` 1.0,
   `alluvial` 1.1, `black` 1.3, `clay` 1.35, anything else 1.0),
7. clamped to 5-95 and rounded to an integer.

The response labels this on every surface: `soil_moisture_detail.source` is
always `"estimated"`, `soil_moisture_detail.method` is
`"heuristic_weather_soil_retention"`, `soil_moisture_detail.assumption` states
that no in-situ sensor is deployed, `watering.inputs_used.soil_moisture_source`
and `fertilizing.inputs_used.soil_moisture_source` repeat it, and
`inputs_summary.soil_moisture_source` summarises it.

Version 1 used `random.randint(20, 80)` here, so two identical requests could
disagree and the email copy could contradict the dashboard. The current
implementation is deterministic and is computed identically in
`/api/sessions/{session_id}/notify`, so the two surfaces agree.

The same estimate is also what drives the `low_moisture`, `ideal_moisture`,
`high_humidity`, `sandy_soil` and `clay_soil` advisory rules. Those rules are
therefore conditional on an estimate, not on a measurement.

### 12.3 The advisory modules are rule-based, not learned

`backend/recommendation_engine.py` and `backend/climate_engine.py` are
**rule-based decision engines**. They consist of explicit `if`/`elif` branches
carrying the original project's agronomic assumptions. They are not trained on
data, and they are not agronomically validated. Every output carries
`"method": "rule_based_decision_engine"` so it cannot be mistaken for a model
output.

The requirement table they use (`water_liters_min`, `water_liters_max`,
`fertilizer_type`, `fertilizer_freq_days`) covers 12 crops and is returned to the
client as `crop_requirement`. For a crop outside that list the **Tomato** row is
substituted; `crop_supported` is `false` in that case and must be checked before
presenting the numbers.

Two further honesty notes carried in the response:

- `et0_estimate` is a `simplified_hargreaves_type_estimate`, **not** FAO-56
  Penman-Monteith. The `limitations` field states that wind speed, latitude and
  day-of-year are not modelled. Solar radiation is `null` because the free
  weather tier does not provide it - no value is fabricated.
- `current.solar_radiation` is always `null` and
  `current.solar_radiation_available` is always `false`, for the same reason.

The disease advisory text returned as `cure` on `/api/predict/disease` is
**template-generated** from project-authored guidance keyed by a disease
keyword, with `method: "template_generation"` semantics and
`source: "project_authored_general_guidance"` on every step. It is not from a
cited agronomic source and is not authoritative; step 3 always directs the user
to the local agricultural extension office.

The `severity` band on a prediction is a keyword lookup over the predicted class
name. It is a documented heuristic and is not clinically or agronomically
validated.

### 12.4 A prediction with `status: "uncertain"` means the top score was below the confidence floor

`status` is derived, in this order, in `backend/ml_service.py`:

1. If the pipeline returned **no detections at all**, `status = "unknown"`.
2. Otherwise, if the top detection's score is **below** `ML_CONFIDENCE_FLOOR`
   (default `40.0`, a percentage), `status = "uncertain"`.
3. Otherwise, if the top label is a healthy class, `status = "healthy"`.
4. Otherwise, `status = "diseased"`.

So `uncertain` does **not** mean "a novel disease was found" and it does not
mean "healthy". It means: *the model produced a top class, but its confidence
was below the configured floor, so the result is not being presented as a
diagnosis.* The accompanying fields are consistent with that reading:

| Field | Value when `status` is `uncertain` |
|---|---|
| `confident` | `false` |
| `requires_expert_review` | `true` |
| `notice` | Non-null: asks for a clearer close-up leaf photo in daylight, or an expert |
| `disease_name`, `severity`, `is_healthy` | Still populated from the top-1 label, for history completeness |
| `confidence_floor` | Echoed so the client can show the threshold that was not met |

Consequences to be aware of:

- The record is still stored and still counted in `/api/predictions/stats`, where
  it lands in `diseased` or `healthy` according to its label. `diseased` is
  therefore not a count of confirmed diagnoses.
- `severity` is still reported for an `uncertain` result. It reflects the class
  name, not a verified assessment.
- Version 1 returned a confident label for any image. The floor exists so that
  out-of-distribution and poor-quality photographs are flagged rather than
  asserted.

A prediction with `status: "diseased"` or `"healthy"` is likewise a model
classification from a single image. The annotation returned in
`annotated_image_base64` is a caption bar, not a bounding box or a Grad-CAM heat
map - the model classifies and does not localise.

### 12.5 Weather provenance

Every weather block carries `data_source` and `simulated`:

| `data_source` | `simulated` | Meaning |
|---|---|---|
| `openweathermap` | `false` | Live provider response, authenticated with `OPENWEATHER_API_KEY`. |
| `simulated` | `true` | Locally generated labelled fallback, produced only when `ALLOW_SIMULATED_WEATHER=true`. `condition` is the literal string `"simulated"`, `feels_like` and `measured_at` are `null`, and `simulation_reason` explains the fallback. |

`ALLOW_SIMULATED_WEATHER` defaults to true in every environment except
`production`/`prod`. In production, an unreachable provider produces `503` on
`/api/sessions/{id}/weather`, `/api/sessions/{id}/recommendations` and
`/api/sessions/{id}/notify` instead of silently serving made-up weather.

### 12.6 Finance and analytics provenance

| Quantity | Source | Caveat |
|---|---|---|
| Investment, revenue, profit, margin | Arithmetic over the rows the user submitted | Only as complete and as honest as the daily logs. `total_yield` ignores any harvested session that lacks a `market_price`. |
| `profit_margin_percent` | `net_profit / total_investment * 100` | `0.0` when there is no investment; not "break even". |
| `resource_timeline` | Daily logs, bucketed by date | The three parallel arrays share one date axis; the cumulative arrays only advance on dates that actually have a log. |
| `crop_distribution` (plant) | Sum of `area_cents` per crop | Area, not a count of sessions or plants. |
| `animal_distribution` | Sum of `animal_count` per type | Head count, not value. |
| `deaths_today` | Stored as submitted | Never subtracted from `animal_count`, yield or revenue by any endpoint. |
| `animals_sold` on close-out | Stored as submitted | Not validated against `animal_count`. |

Every route in `backend/main.py` uses its docstring as the OpenAPI `description`,

following are the cases where the code and its own docstring or summary do not
line up. Nothing here is a functional bug; each item is a documentation defect
worth recording.

| # | Endpoint | Docstring / summary says | Code actually does |
|---|---|---|---|
| 1 | `GET /api/sessions/{session_id}/weather` | "Current weather + forecast for the session location. `current` carries `data_source`/`simulated` flags so the UI and the paper can distinguish live values from labelled fallbacks." | The description does not mention the `days` query parameter at all (default `5`, clamped to 1-5), and does not mention that the route raises `503` when live weather is unavailable and simulation is disabled. | 2 | `GET /api/predictions` | "Detection history for the authenticated user (now timestamped)." | Also accepts `limit` and silently clamps it to 1-200. Neither the parameter nor the clamp is mentioned. |

  when no forecast item falls inside the 24-hour window, or when the forecast
  lookup fails outright. The docstring does not mention the `None` case.
- `recommendation_engine.get_crop_requirement` docstring: "Requirement row for a
  crop, **with a reported fallback** (never silent)". The function returns only
  the requirement row; the substitution to the `Tomato` row is not reported in
  its return value. A caller can only detect the fallback by comparing the
  request's `crop_type` with the response, or by reading `crop_supported` from
  the route.
- `main.py` module docstring: "See API_DOCUMENTATION.md for the endpoint
  reference." That file did not exist in the repository before this one.

## Appendix C: error code summary

Status codes that can actually be produced by the code, and by which routes.

| Status | Routes that can produce it | Trigger |
|---|---|---|
| `400` | `POST /api/auth/register` | Password fails the strength policy; email already registered |
| | `POST /api/auth/login` | Unknown email or wrong password |
| | `POST /api/auth/reset-password` | Unknown email, no outstanding OTP, expired OTP, incorrect OTP, weak new password |
| | `POST /api/predict/disease` | Upload validation (no file, bad content type, bad extension, empty file) or image decode / minimum-dimension / max-pixel failure |
| | `POST /api/sessions/{id}/notify` | The account has no email address on file |
| `401` | All 24 authenticated routes | Missing, malformed, tampered or expired token; non-integer `sub`; `sub` pointing at a missing account |
| `403` | `POST` and `GET /api/sessions/{id}/daily_logs` | Session owned by another account, or `user_id IS NULL` |
| | `POST /api/sessions/{id}/harvest` | as above |
| | `GET /api/sessions/{id}/weather` | as above |
| | `GET /api/sessions/{id}/recommendations` | as above |
| | `POST /api/sessions/{id}/notify` | as above |
| | `POST` and `GET /api/animals/{id}/daily_logs` | Animal session owned by another account, or `user_id IS NULL` |
| | `POST /api/animals/{id}/close` | as above |
| `404` | The same 9 routes that can produce `403` | No farming / animal session with that id |
| `409` | `POST /api/sessions/{id}/harvest` | Session already harvested |
| | `POST /api/animals/{id}/close` | Session already closed |
| `413` | `POST /api/predict/disease` | Upload larger than `MAX_UPLOAD_BYTES` (default 8 MB) |
| `422` | Every route except `GET /api/health`, `GET /api/system/info`, `GET /api/crops` | Schema violation: missing field, wrong type, string or number out of range, non-integer `session_id` / `limit` / `days` |
| `429` | `POST /api/auth/register` | Rate limit scope `register` (default 20 per window) |
| | `POST /api/auth/login` | Rate limit scope `login` (default 10 per window) |
| | `POST /api/auth/forgot-password` | Rate limit scope `forgot` (default 5 per window) |
| | `POST /api/auth/reset-password` | Rate limit scope `reset` (default 10 per window), **and** `OTP_MAX_ATTEMPTS` exhausted (default 5, no `Retry-After`) |
| | `POST /api/sessions/{id}/notify` | Rate limit scope `notify` (default 5 per window) |
| `500` | All 30 routes | Unhandled exception, via the global handler. Also explicitly raised by `POST /api/predict/disease` for model load / inference failure. |
| `502` | `POST /api/sessions/{id}/notify` | SMTP delivery failed |
| `503` | `GET /api/sessions/{id}/weather` | Live weather unavailable and `ALLOW_SIMULATED_WEATHER=false` |
| | `GET /api/sessions/{id}/recommendations` | as above |
| | `POST /api/sessions/{id}/notify` | as above, or email not configured on the server |

The following are **not** producible by any route in this API: `405` and `406`
(no route defines method overrides or content negotiation), and `409` on any
route other than the two close-out routes listed above. `429` is possible only on
the five routes that carry a rate-limit dependency.

## Appendix D: relevant configuration

All values are read from the process environment, optionally seeded by
`backend/.env`. Nothing in the API hard-codes these. `GET /api/system/info`
exposes a secret-free subset of them at runtime.

**Identity and network**

| Variable | Default | Effect on this API |
|---|---|---|
| `APP_ENV` | `development` | Reported by `GET /api/health`. `production`/`prod` changes the simulated-weather default and enables production password rules. |
| `APP_VERSION` | `2.0.0` | Reported by `GET /api/health` and `GET /api/system/info`. |
| `API_HOST` / `API_PORT` | `127.0.0.1` / `8000` | Bind address. Loopback by default. |
| `API_BASE_URL` | `http://localhost:8000` | The absolute base to publish to clients. |
| `CORS_ORIGINS` | 4 localhost origins | Allowed CORS origins. |

**Authentication**

| Variable | Default | Effect on this API |
|---|---|---|
| `JWT_SECRET` | generated per process | Signing key for access tokens and the OTP digest. Unset means tokens stop working after a restart; `validate_startup()` flags this. |
| `JWT_ALGORITHM` | `HS256` | Token signing algorithm. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `720` | `expires_in_minutes` in the register and login responses. |
| `ALLOW_LEGACY_USER_HEADER` | `false` | When `true`, `X-User-Id` is accepted again (with a warning log). When `false`, the header is ignored and the request gets `401`. |
| `PASSWORD_MIN_LENGTH` | `8` | Strength policy on register and reset. |
| `OTP_LENGTH` | `6` | Digits in the emailed reset code. |
| `OTP_EXPIRY_MINUTES` | `10` | Reset-code lifetime. |
| `OTP_MAX_ATTEMPTS` | `5` | Incorrect-code attempts before `429`. |

**Rate limiting** (in-memory, per process, keyed on scope + client IP)

| Variable | Default |
|---|---|
| `RATE_LIMIT_ENABLED` | `true` |
| `RATE_LIMIT_WINDOW_SECONDS` | `300` |
| `LOGIN_RATE_LIMIT` | `10` |
| `REGISTER_RATE_LIMIT` | `20` |
| `FORGOT_RATE_LIMIT` | `5` |
| `RESET_RATE_LIMIT` | `10` |
| `NOTIFY_RATE_LIMIT` | `5` |
| `TRUST_PROXY_HEADERS` | `false` - when `false`, `X-Forwarded-For` is ignored so a caller cannot rotate identities to bypass the limit. |

**Machine learning**

| Variable | Default | Effect on this API |
|---|---|---|
| `MODEL_DIR` | `backend/models/plant_disease_model` | Where the classifier is loaded from. A missing directory makes `/api/predict/disease` return `500`. Only the folder **name** is exposed by `/api/system/info`. |
| `ML_DEVICE` | `auto` | `auto` uses CUDA when available, else CPU. |
| `ML_TOP_K` | `5` | `len(prediction.detections)`. |
| `ML_CONFIDENCE_FLOOR` | `40.0` | The threshold below which `status` becomes `uncertain`. |
| `ML_WARMUP_ON_STARTUP` | `true` | When `false`, `ml.loaded` in `/api/system/info` is `false` until the first prediction. |

**Uploads**

| Variable | Default | Effect on this API |
|---|---|---|
| `MAX_UPLOAD_BYTES` | `8388608` (8 MB) | Above this, `POST /api/predict/disease` returns `413`. |
| `ALLOWED_IMAGE_TYPES` | `image/jpeg`, `image/png`, `image/webp` | Content types accepted. |
| `ALLOWED_IMAGE_EXTENSIONS` | `.jpg`, `.jpeg`, `.png`, `.webp` | Filename extensions accepted. |
| `MIN_IMAGE_DIMENSION` | `32` | Minimum width and height in pixels. |
| `MAX_IMAGE_PIXELS` | `25000000` | Decompression-bomb guard on `width * height`. |

**Weather and email**

| Variable | Default | Effect on this API |
|---|---|---|
| `OPENWEATHER_API_KEY` | empty | `weather_configured` in `/api/system/info`. Empty means weather is simulated or `503`. |
| `OPENWEATHER_BASE_URL` | OpenWeather 2.5 base | Provider endpoint. |
| `WEATHER_TIMEOUT_SECONDS` | `10` | Per-request timeout. |

**Storage**

| Variable | Default | Effect on this API |
|---|---|---|
| `DATABASE_PATH` | `backend/database.db` | SQLite file. Relative values are anchored to the project root, not the working directory. |
| `DATABASE_ENABLE_FOREIGN_KEYS` | `true` | Enables `PRAGMA foreign_keys=ON` per connection, which SQLite ignores by default. |
| `DATABASE_ECHO` | `false` | SQL echo in logs. |

provider API key and the SMTP password are read from configuration only, and the
SMTP password is additionally registered with the log redaction filter so it can
never be written to a log line.
